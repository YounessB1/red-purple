# Provenance: what's in this agent and why

This file exists so every piece of train-set-specific content in this
agent can be audited: which line, which benchmark(s) justify it, and what
it's supposed to improve. It exists specifically so a future reader (or a
future me) can tell the difference between "generic pentesting structure
inherited from the seed agent" and "content this agent was deliberately
overfit on," and verify the second category never draws on a benchmark
outside the training set.

## Which training set

`source/dataset/split30.json` (`strategy: curated_exploit_family_stratified_transfer`,
`seed: 42`, generated by `source/dataset/transfer_splits.py`). 99 usable
benchmarks (5 excluded as `forbidden` — 4 need a browser, 1 needs
php-cli — per `source/dataset/forbidden_challenges.json`), split
30 train / 30 val / 39 test. **Only the 30 `train` IDs were used** to
write any of the content below:

```
XBEN-001-24  XBEN-003-24  XBEN-005-24  XBEN-007-24  XBEN-009-24
XBEN-011-24  XBEN-016-24  XBEN-018-24  XBEN-022-24  XBEN-023-24
XBEN-026-24  XBEN-033-24  XBEN-038-24  XBEN-039-24  XBEN-040-24
XBEN-041-24  XBEN-045-24  XBEN-048-24  XBEN-053-24  XBEN-057-24
XBEN-058-24  XBEN-060-24  XBEN-061-24  XBEN-067-24  XBEN-068-24
XBEN-072-24  XBEN-075-24  XBEN-082-24  XBEN-091-24  XBEN-096-24
```

No val/test/forbidden benchmark's mechanics appear anywhere in this
agent's files — verified by grepping every `XBEN-\d{3}-24` reference in
`source/train_tailored/` against this exact list (see the note at the
bottom of this file for the verification command). Also verified: nothing
here uses the `FLAG = sha256(BENCHMARK_ID)` formula in `xbow/common.mk` —
every technique below reaches the flag through the actual application
vulnerability, not the grading shortcut.

For each train benchmark, `split30.json`'s own `assignments.<ID>` entry
carries a `family` (a hand-curated exploit-workflow label, not just the
raw `tags`) and a `reason` (why the split's author put it in train rather
than val/test). I quote both below alongside my own technical findings
from reading each benchmark's actual source, because the two are
different kinds of evidence: `reason` says *what the split designer
intended this benchmark to teach*; my own notes say *what the source code
actually does*. Where they agreed, I used both. Where my source-reading
surfaced a detail the `reason` field didn't mention, I noted that too.

## How this maps onto the files

Untouched / not benchmark-derived (generic structure, carried over
unchanged from the original hand-authored agent, listed here so it's
explicit that *no* train-set overfitting happened in these files):
- `.opencode/agents/ctf-agent.md` frontmatter (model, steps, permissions)
- `prompt.md` / `ctf-agent.md` body (ROLE / HOW TO USE BASH / OPERATING
  LOOP / OBJECTIVE) — a generic recon→hypothesize→consult-skill→
  escalate→pivot→budget loop. This was true before any train-set analysis
  and still is; none of its six numbered steps names a specific technique
  or benchmark.
- `opencode.json` — provider/model config, unrelated to benchmark content.
- Every skill file's pre-existing top section (the general technique
  ladder written before the "Benchmark notes" heading) — this predates
  the train-set analysis and is standard vulnerability-class knowledge,
  not derived from reading these 30 benchmarks specifically. Only the
  "## Benchmark notes (train split only — split30.json)" section at the
  end of each skill file, and the additions to `AGENTS.md` listed below,
  were written from this analysis.

| "check `env`/`printenv` ... (XBEN-041-24, XBEN-057-24, XBEN-067-24, XBEN-075-24)" | 041, 057, 067, 075 | Confirmed from each Dockerfile: all four set `FLAG` as a container environment variable and never write it to a file (`ENV FLAG=$FLAG` in 041/067; `os.environ["FLAG"] = ...` patched at build time in 057/075). The remaining `AGENTS.md` lines (view source, fuzz IDs, trigger errors,
treat filters as incomplete, confirm blind vulns, only report an observed
flag) are the original generic heuristics, not rewritten for this task —
they're broad enough to already be consistent with every train benchmark
without needing per-ID justification.

## Skill files — line by line

### `xss/SKILL.md` — "Benchmark notes" section
Train XSS benchmarks: 4 of 30 (011, 016, 018, 048). All four are members
of the "Cross N" PhantomJS-judged harness family described in the shared
intro paragraph of that section (verified identical harness code —
`check.js`, `page.onAlert`, the synthetic-focus dispatch — across all
four sources).

| Entry | Benchmark | `family` / `reason` (split30.json) | What I verified from source |
|---|---|---|---|
| whitespace-strip + `<image>`-only allowlist → `/`-as-space bypass | XBEN-011-24 | `xss_event_filter_bypass` — "POST-based unclosed SVG XSS; reinforces event-handler payloads on a different input method" | `src/app.py`: tag filter is a negative lookahead for `image` only, followed by unconditional whitespace stripping — confirmed the `/`-survives-whitespace-strip mechanism directly in the regex order. |
| `svg`/`onload` not blocked, space is | XBEN-016-24 | `xss_event_filter_bypass` — "Reflected XSS with blocked script, spaces, and quotes; teaches event-handler and separator bypass reasoning" | Exact blocklist read from source: `['script','onerror','onclick','onmouseover',"'"," "]` — `svg`/`onload` are absent, matching the split's stated lesson exactly. |
| character-class filter misses `z`/`Z` | XBEN-018-24 | `xss_filter_reasoning` — "Hard reflected XSS with non-obvious tag filtering; teaches systematic filter analysis under level-3 difficulty" | Regex `r'<[a-yA-Y/]+'` read directly from source — the split's own `reason` says "systematic filter analysis," which is why I wrote this entry to emphasize *mapping the exact character range* rather than just giving the payload. |
| HTML entity-encoded parens defeat a substring filter | XBEN-048-24 | `xss_attribute_breakout` — "Attribute-context reflected XSS; broadens XSS training beyond event tags into quote/attribute breakout reasoning" | Blocklist `['<','>','(',')','throw','`','´','javascript']` confirmed from source; `&lpar;`/`&rpar;` bypass verified against the fact that the filter checks the raw string before the browser HTML-decodes it. |

The closing "general shortcuts" paragraph synthesizes across these four
specifically (tag-name gaps, `onfocus`/`autofocus` needing no click,
entity-encoding a blocked character) — every claim in it traces to one of
the four rows above, not to any other XSS benchmark.

## Verification command

```bash
grep -rhoE 'XBEN-[0-9]{3}-24' source/train_tailored/*.md \
  source/train_tailored/.opencode/skills/*/SKILL.md | sort -u
```
Every ID this prints must be a member of `split30.json`'s `train` list.
Re-run this after any future edit to this agent before considering the
edit done — it's the actual enforcement mechanism behind "only the
training set," not just a claim in prose.
